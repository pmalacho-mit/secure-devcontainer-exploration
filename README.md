# secure-devcontainer-exploration

This dev container lets code — including coding agents — build, run, and `docker exec` sibling containers on the host Docker daemon, while preventing (or at least attempting to) those containers from gaining more privilege than the dev container itself, or being used to escape to the host. It's a two-layer gate in front of the Docker socket: a maintained endpoint-level proxy that holds the real socket ([tecnativa/docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy)), plus a small custom body-inspecting shim — a Go program that parses each request with the Docker daemon's *own* standard library and API types — that enforces a per-request "same access, or less" policy.

## Adapted from

The structure and hardening are adapted from Daniel Demmel's [*Coding agents in secured VS Code dev containers*](https://www.danieldemmel.me/blog/coding-agents-in-secured-vscode-dev-containers). Taken directly:

- The **threat model** — limit the blast radius of untrusted code: supply-chain attacks (malicious `npm` packages), prompt injection, and plain agent mistakes.
- The **compose-based dev container with a Docker socket proxy sidecar** ([tecnativa/docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy)), where the app reaches Docker only through `DOCKER_HOST`.
- The **privilege hardening**: no `sudo` in the image, `cap_drop: ALL`, and `no-new-privileges: true`.
- The recognition that some risks (network egress, workspace writes) are **accepted** because development needs them.

## Where it differs — and why

The reference runs the socket proxy **read-only** (`POST`, `EXEC`, `BUILD` all off): the agent can inspect containers and read logs, but can't create, exec, or build. That's the right call when the agent only needs to *observe* Docker. 

My projects' workflows can **_not_** live with that, as they freely re-build and run containers, and in the case of a browser-testing image, rely on `exec`ing (using `playwright-cli` inside the container). So rather than *removing* those capabilities, it *constrains* them:

1. **Create is allowed but bounded.** tecnativa can only gate whole endpoints ("may you create containers at all?"), never request contents. So a body-inspecting shim sits in front of it, parses each `POST /containers/create`, and rejects anything that would grant a sibling more than the dev container has: privileged, added capabilities, devices, host or cross-container namespaces (including the **cgroup** namespace — `--cgroupns=host`), **any host bind mount or host-bind volume at all**, weakened seccomp/apparmor, a `/proc` mask weaker than the daemon default (a `MaskedPaths`/`ReadonlyPaths` override — e.g. `MaskedPaths:[]`, which would un-mask `/proc/kcore` and make `/proc/sysrq-trigger` writable), or mounting a globally-shared system volume (the VS Code `vscode` server-cache volume, which every project's dev container shares — a cross-project code-execution channel). Container creation becomes a bounded operation instead of an escape primitive. Beyond *denying* added capabilities, the shim also **force-drops** every sibling to `CapDrop:["ALL"]` and re-adds only a **configurable, clamped allowlist** (`SIBLING_CAPS`, default a "mostly safe" set — `SETUID,SETGID,CHOWN,DAC_OVERRIDE,FOWNER,NET_BIND_SERVICE,NET_RAW`); the allowlist is clamped to Docker's default caps in the shim, so it can tighten or re-pick but never grant a cap beyond the defaults (`=default` opts out, `=none` drops everything — DESIGN.md cont. 22). (Siblings never mount host paths — they share state with the dev container over the network, `docker exec`, and the build context — so there is no host path for the daemon to resolve at mount time, and therefore no bind-source symlink/traversal/TOCTOU escape class to defend; see DESIGN.md cont. 7.) The shim routes on the **cleaned** request path (`path.Clean`), so a non-canonical path that resolves to a gated endpoint (`//containers/create`, `/foo/../containers/create`) is policed identically to the canonical one — not left to survive on the daemon happening to `301` dirty paths (DESIGN.md cont. 19).

   **Parsing with the daemon's own code — no parser differential.** A subtle but recurring class of bypass is "the shim judged a *different* request than the daemon executed." Earlier the shim was written in Python and approximated the daemon's parsing — and every place the two parsers disagreed was an escape: a re-cased field (`binds` vs `Binds`: Python dicts are case-sensitive, Go's `encoding/json` matches struct fields case-insensitively), a Unicode-folded key (`Bindſ` with a long-s: Python's `str.lower()` ≠ Go's `bytes.EqualFold`), and a percent-encoded path (`/containers/%63reate`: a regex on the raw path ≠ the daemon routing the URL-decoded path) were each a confirmed host-file read. So the shim was **rewritten in Go** and now parses each request with the daemon's *own* stdlib and `api/types` structs: the path is matched on `net/http`'s decoded form, and the body is unmarshalled into the daemon's `container.Config`/`HostConfig`/`mount.Mount`/… so Go's `encoding/json` does the *identical* case- and Unicode-folding the daemon does. A re-cased or re-encoded field lands in exactly the field/route the daemon will use and trips the one ordinary check — the whole differential class is closed by construction, with no key-normalization and no "lowercase-metadata" house rule. Ordinary traffic also rides `net/http`'s framing, which reads one request per connection and never forwards pipelined bytes, so the old request-smuggling surface is gone there — with one exception that bit back: the **connection-hijack relay** (exec/attach/`/session`) is necessarily hand-rolled, and it reintroduced the pipelined-create smuggle until it was made to confirm a `101` upgrade before relaying anything (cont.17). See DESIGN.md cont. 14–17. The shim's Go toolchain and `moby/moby/api` types are pinned to the host daemon's own versions (Go toolchain ← Server Go version, API types ← Server API version) and re-synced automatically on rebuild via `sync-shim-to-host.sh`.

2. **Exec is label-gated, not blocked.** The reference blocks `docker exec` and routes interaction over HTTP instead. This project needs exec — but enabling it naively would let code `docker exec` into the *proxy* container (which holds the real socket) and escape. So the shim stamps an ownership label on every container it creates and permits exec (and `attach`/`docker cp`) **only** into labelled containers: your own test containers, never the proxy or anything else on the host. The ownership stamp is **per-project** (`authz.owned=project:<name>`, not a global `1`), so one project's shim never recognises another project's siblings as its own — two dev containers on the same daemon can't exec/`cp` into each other's created containers (DESIGN.md cont. 19).

   **Cross-container reads are gated too.** The read endpoints that leak another container's contents — `export` (the whole container-layer filesystem as a tar), `logs`, `top`, `changes`, and `inspect` (`/json`) — were previously ungated (they streamed straight through to tecnativa, which filters by endpoint, not target). They're now gated by **readability**: a container is readable only if you own it *or* it's in your own Compose project. So the dev container can still inspect itself, its network, and its own infra (the workflow needs this), and read its own created siblings — but a *sibling project's* containers (including another agent's home dir and session transcript, which `docker export` would otherwise dump) are denied. Image export (`docker save`, `/images/{id}/get`) is denied outright (images carry no ownership label). See DESIGN.md cont. 19, assessment finding F1.

3. **Neither privileged layer has a network; both are reached over unix sockets.** Because creates are allowed, the design also has to stop those siblings from reaching the privileged proxy. The proxy (tecnativa) runs `network_mode: none` — it's off **every** Docker bridge, so there is simply no IP for any sibling (or even a `--network=host` build, which runs in the VM root netns) to route to. The shim reaches it over a **unix-domain socket** on a shared volume; a unix socket is a mount-namespace object, unreachable from anything that only shares the network namespace. **The shim itself now lives off all networks too (cont. 20).** It used to listen on `tcp://docker-authz:2375` on the project's `_dev` bridge — but a `_dev` bridge is joinable by *any* container on the daemon, and the shim authorises the *request*, not the *caller* ("same-project readable" trusts whoever can reach it). So a foreign tenant could pivot a sibling onto a *victim's* `_dev`, reach the **victim's** shim, and have it `export`/`inspect` its own (same-project) containers — a confirmed cross-tenant read (four independent red-team agents found exactly this). The shim now listens on a **unix socket** on an `app-sock` volume mounted only into the dev container and runs `network_mode: none`; `DOCKER_HOST` is `unix:///run/app/docker.sock`. There is no shim IP for any sibling — own or foreign — to pivot to, so the per-project read logic is sound by construction. The shim refuses to mount **either** socket volume into a sibling (`…gate-sock`, `…app-sock`), and namespace/`VolumesFrom` sharing is rejected outright. Siblings that need to reach servers inside the dev container (e.g. the browser image driving tests) join the dev container's network as ordinary **peers** (`--network <project>_dev`), never by sharing its network namespace — same reachability, strictly less privilege. *(See DESIGN.md cont. 9–10 for the same move applied to the proxy, and cont. 20 for the shim.)*

4. **Fail closed on unparseable bodies.** Any create whose body the shim can't parse is denied — which also avoids the class of authz bypass where a request reaches the policy without its body.

In short: the reference removes dangerous capabilities for an agent that only needs to read Docker; this project keeps the capabilities it genuinely needs and instead constrains them, preserving the invariant that siblings never exceed the dev container and can't reach the privileged layer.

### Per-devcontainer isolation

Each dev container gets its **own** Docker network rather than a shared, fixed-named one. The Compose network is left unnamed, so Compose scopes it to the project (`<project>_dev`), and since the devcontainer CLI assigns each dev container a distinct project, two projects never collide. The app keeps discovering its network programmatically (e.g. `devcontainer.network()`) instead of relying on a hard-coded name — which is the whole point of leaving it unnamed.

Since cont. 10 the proxy lives on **no** network (reached over the unix socket above), so there is no "gate network" to join, enumerate, or wire onto after the fact — that whole attack class is closed by construction. The shim still carries its gate-network recognisers (by `…_gate` suffix and by runtime-discovered name/id, plus a `docker network connect` guard) but they're now inert backstops: nothing hosts the proxy on a bridge. Namespace sharing (`--pid`, `--ipc`, `--network container:…`, host namespaces) is rejected outright, since those would otherwise be routes to a sibling's or the proxy's process/network.

Since cont. 20 each project's `_dev` network is also walled off from *other* projects: the shim **denies creating-onto, connecting-onto, or inspecting any network owned by a different Compose project** (`com.docker.compose.project != ours`), while still allowing your own `<project>_dev`, the built-in `bridge`/`none`, and unlabeled user networks. This closes the cross-tenant pivot at the network-join layer (the structural fix is the shim being off-network at all — above) and stops `docker network inspect` from leaking a foreign project's container IPs. Container **lifecycle** (`stop`/`kill`/`restart`/`rename`/`rm`) is likewise owned-only now, symmetric with `exec`/`cp`.

### VS Code IPC sockets — partially adopted (defence-in-depth)

The reference also hardens **VS Code's injected IPC sockets and env vars** (`SSH_AUTH_SOCK`, the git-credential broker, `VSCODE_IPC_HOOK_CLI`, etc.) — a separate container-escape surface the Docker gate never touched. Since cont. 13 this project adopts a **scoped** version: the host-reaching **credential/agent** channels (the forwarded SSH agent and the dev-containers git-credential broker) are nulled from the environment and swept from `/tmp`. But these run **in-container, at the agent's own privilege**, so by this repo's own governing principle they're defeatable by a fully adversarial same-privilege attacker (who can just re-glob the socket) — the tamper-resistant control is **host-side** (disable SSH-agent and git-credential forwarding in your VS Code settings); treat the in-repo layers as depth behind that. The **editor** IPC (`VSCODE_IPC_HOOK_CLI`) is deliberately left intact to preserve in-editor agent integration. The project also intentionally diverges on **SSH keys**: the reference doesn't mount them at all, whereas this project keeps them available (and monitored separately) rather than removed.

### VS Code extension host — uid-separate the agent from it (cont. 21)

The VS Code **extension host** (which holds the `vscode.workspace.fs` / `vscode-local://` host-FS API) and the agent's shell used to run as the **same uid** (`remoteUser: vscode`). Signals are not ptrace, so a same-uid process could `kill -USR1` the extension-host node process to open its V8 inspector, attach over CDP (arbitrary JS *inside* the extension host), and read/write arbitrary **host** files — with no Docker call, so the whole gate is bypassed. This is a property of running untrusted code at the extension host's own uid; no in-container Docker control can revoke it.

The fix is **uid separation**: a separate, unprivileged **`agent`** user (uid 2000, no sudo) runs the agent CLI and everything it spawns (npm installs, the workflow, every shell command — the untrusted surface), while the VS Code server + extension host stay `vscode`. A `kill -USR1` from `agent` to the vscode-owned extension host now returns **EPERM**, so the inspector never opens. Two hooks make it stick: (1) the integrated terminal drops into `agent` (a `sudo -u agent -i` profile), covering shells *you* open; and (2) — the **load-bearing** one — `claudeCode.claudeProcessWrapper` points the Claude Code extension at `/usr/local/bin/claude-as-agent`, which re-execs the CLI as `agent`. The second hook is essential because the extension spawns its **bundled** `claude` binary as a *direct child of the extension host* (same uid, not a terminal, by absolute path) — confirmed via the live process tree — so the terminal profile alone would leave Claude's Bash tool running as `vscode`. With the wrapper, every command Claude runs is `agent`. The editor and the *trusted* `anthropic.claude-code` extension itself are unaffected.

This is the structural in-container fix for the *same-uid-shell* hijack. It does **not** close a compromised *trusted* extension running inside the extension host (supply chain of an allowed extension, or that extension's own in-process tool execution) — that remains the **host-side** boundary (the enforced `extensions.allowed` allowlist + Workspace Trust, mirrored into host user settings; see above). On a **native-Linux** host you may need `/workspace` group-writable for `agent` (uid 2000 in the `vscode` group); on Docker Desktop the file-share is permissive. Run `./test-escape.sh` from the (default) agent terminal — its F1 case asserts the agent *cannot* signal the extension host. See `docs/DESIGN.md` cont. 21.

### VS Code shared server-cache volume — disable it host-side

The VS Code **Dev Containers extension** creates a single, **globally-named** Docker volume called `vscode` and mounts it into **every** dev container on the machine at `/vscode` — a shared cache for the VS Code server and extensions. Because it isn't project-scoped, it's a cross-project channel: a root write into it lands in *every other* project's dev container, and the server binaries under it are on each container's `PATH`, so it's a code-execution foothold between projects (assessment finding F2 / DESIGN.md cont. 19). The shim now refuses to let a *sibling it creates* mount that volume (`DENY_VOLUMES`, default `vscode`), but the **share itself is created by VS Code over the host socket, before the shim exists** — so the shim can only stop the agent from getting an *extra* handle, not remove the cross-container share.

The real fix is **host-side**: disable the cache volume so each container gets its **own** isolated server cache instead of the shared one. Set this in your **host** VS Code **user** `settings.json` (⌘⇧P → *Preferences: Open User Settings (JSON)*; on macOS/Linux `~/.config/Code/User/settings.json`):

```jsonc
{
  // Dev > Containers: Cache Volume — false = per-container server cache, no shared `vscode` volume
  "dev.containers.cacheVolume": false
}
```

This **must** be a host user/profile setting: there is **no** `devcontainer.json` or workspace-settings equivalent — the request to make it per-project was [closed *"not planned"* upstream (vscode-remote-release#11185)](https://github.com/microsoft/vscode-remote-release/issues/11185), so an in-repo value can't enforce it (the same "the real boundary is host-side" caveat as the IPC controls above). **Cost:** the ~100 MB VS Code server (and your extensions) re-downloads/installs **per container and per rebuild** instead of being shared, so first-attach and post-rebuild startup is noticeably slower and disk use rises (one server copy per container). Weigh that against your rebuild cadence.

## Trying it

From inside the dev container, `./test-escape.sh` attempts privileged runs, host/socket mounts, `--pid=host`, `--cap-add`, unconfined **and custom** seccomp/apparmor, joining the gate network **by name and by id**, wiring an existing container onto the gate with `docker network connect`, exec-into-the-proxy, **privileged exec** into an owned container, request smuggling through the upgrade/relay path, **re-cased create fields** (`binds`/`BINDS`/`hostconfig`, same-field case collisions, and Unicode long-s `Bindſ`), **percent-encoded routing** (`/containers/%63reate`), a **non-canonical create path** (`//containers/create`), `--cgroupns=host` and a **`MaskedPaths` override**, mounting the shared **`vscode` system volume**, **cross-tenant reads** (`docker export`/`logs`/`inspect` of a foreign-project container), the **cross-tenant network pivot** (running/connecting a sibling onto a *foreign* `_dev` network, inspecting a foreign network, and `rename`/`stop`/**`start`**/**`disconnect`** of a foreign container/network), `--network=host`/`container:` **builds**, mounting the **gate** or **app socket** volume, a **colon-separated custom seccomp** profile, daemon-global **`prune`**, **`docker save`** (plural `/images/get`), and a **macvlan** network — all of which should be blocked — plus, as a separate door the Docker gate can't touch, the **VS Code extension-host inspector hijack** (`kill -USR1` the same-uid extension host → CDP → host FS), which is blocked by running the agent as a **separate `agent` uid** (cont. 21) — plus a plain run, a plain build, joining the dev network as a peer, a benign all-lowercase create, exec/`cp` into an owned container, `--cgroupns=private`, reading/inspecting your **own** and **same-project** containers, and `docker ps`, which should be allowed. It also asserts **both** privileged layers are off all networks (no IP — the proxy *and* the `docker-authz` shim) and that `DOCKER_HOST` is a unix socket, and that no `…_gate` network exists. The shim's pure policy logic also has hermetic Go unit tests (`.devcontainer/authz_test.go`), plus daemon-free handler tests that drive a fake upstream: a smuggling-guard test firing the `/session`+pipelined-create exploit and asserting the create never reaches it (`.devcontainer/authz_hijack_test.go`, cont.17), and routing tests asserting a non-canonical-path create is policed and cross-project reads are denied (`.devcontainer/authz_route_test.go`, cont.19) — all run in the shim image's `--target test` build stage (`./test-all.sh`, or `docker build --target test`). Watch decisions stream from the host with `docker compose -f .devcontainer/docker-compose.yml logs -f docker-authz`.
